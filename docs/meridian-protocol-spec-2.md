# ЧАСТЬ A. Добор по первому заходу

## A1. Матрица инкапсуляции

Порядок слоёв снизу вверх (от того, что реально едет по UDP, к тому, что в
итоге попадает в TUN), выведен из `wrapPacketConn`/`wrapPacketListener`
(`raw-gateway-src/main.go-647`) и `serveDTLS`/`serveNoTLS`
(`main.go-1476`, `1406-1450`).

| порт | путь клиента | что летит по UDP до шлюза (порядок снаружи внутрь) | применяется ли obfs |
|---|---|---|---|
| `56004` | через TURN-релей VK | `[TURN-framing, только на участке клиент↔TURN]` → `[obfs-RTP: 12Б заголовок + ChaCha20-Poly1305]` → `[DTLS-запись]` → сырой IP-пакет | **да**, обязательно — иначе `dtls.NewListenerWithOptions` не получит от `wrapListener` ничего осмысленного |
| `56004` | прямой UDP (если `-peer` указывает именно на 56004, второй кандидат `directs`, `session_raw_path.go-409`) | `[obfs-RTP]` → `[DTLS-запись]` → сырой IP-пакет (TURN-framing отсутствует вовсе — сокет клиента пишет прямо шлюзу) | да, так же |
| `443` | прямой UDP (`directPrimaryPort`, первый кандидат) | `[obfs-RTP]` → `[DTLS-запись]` → сырой IP-пакет | да |
| `56005` (умолчание `rawNoTLSPort`) | через TURN-релей VK, capability `RELAY_NOTLS` (`rawRelayNoTLS`) | `[TURN-framing, клиент↔TURN]` → `[obfs-RTP]` → сырой IP-пакет **(DTLS ОТСУТСТВУЕТ вовсе)** | да, obfs — единственный крипто-слой |
| `56005` | прямой UDP, capability `DIRECT_NOTLS` (`rawDirectNoTLS`) | `[obfs-RTP]` → сырой IP-пакет | да, единственный слой |

**Ключевой вывод: `obfs` применяется НА ВСЕХ ТРЁХ ПОРТАХ без исключения.**
На 56004/443 он оборачивает БАЙТЫ DTLS-ЗАПИСИ (obfs снаружи, DTLS внутри —
подтверждено комментарием `main.go-378`: «клиент оборачивает DTLS-байты
в RTP-маскировку перед отправкой» — и механикой `wrapPacketConn`, см. A2: DTLS
у pion работает НАД уже развёрнутым/собранным `wrapPacketListener`, то есть
получает на вход байты, из которых obfs УЖЕ снят). На 56005 obfs — вообще
единственный крипто-слой, DTLS в цепочке нет физически (`serveNoTLS` не
создаёт `dtls.Listener`, `main.go-1450`).

**На порту 443 obfs применяется — да**, подтверждено: `443` обслуживается
той же `serveDTLS`, которая строит транспорт через `listenWrappedDirect`
(`main.go`), то есть точно так же проходит через `wrapPacketConn`
(obfs-unwrap) прежде чем попасть в DTLS-движок pion.

**TURN-framing** (ChannelData 4Б-заголовок или Send/Data indication ~36Б,
числа из `ЗАМЕР-ПРОЦЕССОРА.md` — `[хендофф]`, этим заходом не перепроверял)
существует **только на участке клиент↔TURN-сервер VK** и **никогда не
доходит до шлюза**: TURN-релей — это чистая пересылка UDP-полезной нагрузки,
шлюз получает на своём порту обычный UDP-пакет с тем же телом, что клиент
положил бы туда при прямом подключении. Разницы в обработке на шлюзе между
«через релей» и «напрямую» нет вообще (см. первый документ, 1.1,
`main.go-1347`) — это прямое следствие того, что TURN не добавляет
собственного крипто-слоя поверх пересылаемых байт.

## A2. `wrapKeyStore.Unwrap` — какой листенер зовёт, встречная гипотеза проверена

**Встречная гипотеза («перебор ключей нужен только на бессессионном
`-listen-notls`») — НЕ подтвердилась. Perebor используется на ВСЕХ ТРЁХ
листенерах одинаково**, потому что слой подбора ключа стоит НИЖЕ DTLS
универсально, а не только там, где DTLS нет вовсе.

Цепочка вызовов, `Unwrap` зовётся из `wrapPacketConn.ReadFrom`
(два места — первичный выбор ключа и перевыбор при смене ключа на лету):
```
main.go   key, m, uErr := c.keys.Unwrap(raw, p)     // первый пакет на соединении
main.go   key, m2, uErr2 := c.keys.Unwrap(raw, p)    // текущий ключ не подошёл — пробуем все заново
```
`wrapPacketConn` создаётся в `wrapPacketListener.Accept()` (`main.go`,
конкретно `c := &wrapPacketConn{inner: pc, keys: l.keys}`, `main.go`).

`wrapPacketListener` создаётся ДВУМЯ путями:
1. `listenWrappedDirect(addr, keys, echoProbes, lim)` (`main.go-473`) —
   вызывается из `serveDTLS` (`main.go`, оба тега «релей/56004» и
   «прямой/443»), и результат **передаётся В `dtls.NewListenerWithOptions`
   как транспорт** (`main.go`: `dtls.NewListenerWithOptions(wrapListener,
   ...)`). То есть для 56004 и 443 — **obfs-unwrap (с перебором ключей) стоит
   НИЖЕ DTLS**: pion читает уже освобождённые от obfs байты и разбирает их
   как DTLS-запись.
2. Напрямую в `serveNoTLS` (`main.go-1427`:
   `&wrapPacketListener{inner: dtlsnet.PacketListenerFromListener(inner),
   keys: keys}`) — здесь то же самое `Unwrap` служит **единственным**
   крипто-слоем, DTLS сверху нет.

Почему перебор ключей нужен именно на этом уровне, а не выше: у шлюза до
получения самого первого пакета от адреса **нет никакого способа узнать,
какому паролю он принадлежит** — ни DTLS-сессии, ни TURN-канала с этой
информацией не существует (адрес источника — это адрес TURN-релея или
клиента, но не идентификатор пароля). Единственный способ узнать ключ —
попробовать расшифровать пробный пакет каждым известным ключом и посмотреть,
у какого сойдётся AEAD-тег. Это верно НЕЗАВИСИМО от того, стоит ли сверху
DTLS: DTLS-хендшейк САМ ПО СЕБЕ не начнётся, пока не будет решено, каким
ключом снимать obfs с приходящих байт, — то есть даже для 56004/443 подбор
ключа логически предшествует DTLS, а не заменяется им.

После первого успешного подбора ключ на конкретном `wrapPacketConn`
запоминается (`c.key`, `atomic.StoreInt32(&c.selected, 1)`, `main.go`) и
дальнейшие пакеты того же UDP-«соединения» (pion udp транспорт различает
клиентов по адресу источника, см. комментарий про CID в A3) идут по прямому
пути `obfsUnwrapPacket(c.key, ...)` (`main.go`) без перебора — перебор
повторяется, только если текущий ключ вдруг перестал подходить (ротация
пароля на лету, `main.go-616`, лог `"[WRAP] Обновлён ключ на лету"`).

## A3. Клиентская сторона DTLS — построчно

Найдено три места с идентичным `dtls.Config` (два — общий VPN/socks-путь,
`session.go,611`; одно — RAW, `session_raw.go-595`, релевантно этой
спецификации):

```go
// session_raw.go-595
dtlsCfg := &dtls.Config{
    Certificates:         []tls.Certificate{cert},   // селф-подписанный, генерируется ЗАНОВО на каждую сессию
    InsecureSkipVerify:   true,
    ExtendedMasterSecret: dtls.RequireExtendedMasterSecret,
    CipherSuites:         []dtls.CipherSuiteID{dtls.TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256},
    MTU:                  1100,
}
dtlsConn, err := dtls.Client(pipeB, peer, dtlsCfg)   // session_raw.go
```

- **Сертификат шлюза**: `InsecureSkipVerify: true` (`session_raw.go`) —
  клиент **не проверяет сертификат шлюза вообще**: ни цепочку доверия, ни
  имя хоста, ни pinning. Отключено буквально этим одним полем стандартной
  библиотеки `pion/dtls`, никакой дополнительной логики нет. Подлинность
  канала в этой схеме держится не на PKI, а на том, что оба конца знают один
  и тот же `wrapKey`, выведенный из пароля (obfs снаружи DTLS — см. A1/A2):
  без верного пароля клиент вообще не доберётся до DTLS-хендшейка, потому
  что шлюз не сможет снять obfs с его пакетов.
- **Собственный сертификат клиента**: генерируется заново каждую сессию
  (`cert, err := selfsign.GenerateSelfSigned()`, `session_raw.go`) —
  предъявляется шлюзу, но шлюз тоже его не проверяет содержательно (шлюз
  просто принимает DTLS-клиента, аутентификация клиента идёт через
  application-layer AUTH поверх уже установленного DTLS-канала, см. Блок 1
  первого документа).
- **Cipher suite**: единственный разрешённый —
  `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256` — совпадает с сервером
  (`main.go` шлюза) буквально.
- **ExtendedMasterSecret**: `RequireExtendedMasterSecret` — совпадает с
  сервером (`main.go`) дословно.
- **MTU**: `1100` — совпадает с сервером (`main.go`, `WithMTU(1100)`).
- **Connection ID — РАСХОЖДЕНИЕ, важное.** Клиент **сознательно НЕ
  устанавливает** `ConnectionIDGenerator` в своём `dtls.Config`
  (поля просто нет в структуре, `session_raw.go-595`), тогда как шлюз
  явно объявляет `dtls.WithConnectionIDGenerator(dtls.RandomCIDGenerator(8))`
  (`main.go`). Решение задокументировано развёрнутым комментарием
  прямо над конфигом (`session_raw.go-587`):
  - CID существует ради одной вещи — чтобы сессия пережила смену адреса
    клиента за NAT (переключение по CID, а не по адресу источника, на
    приёме);
  - но у ОБОИХ серверов (шлюз и «основной сервер») листенер строится вручную
    через `pionudp.ListenConfig` + `NewListenerWithOptions`, а не через
    `dtls/listener.go` целиком, а библиотека транспорта
    (`pion/transport/v4@v4.0.1`) раскладывает соединения по `raddr.String()`
    (`udp/conn.go`), не по CID — то есть переживание rebind **не
    работает НА ЭТОМ СТЕКЕ независимо от настроек**, сама выгода от CID здесь
    отсутствует;
  - при этом СТОИМОСТЬ CID реальна: с ним каждая DTLS-запись оборачивается в
    `ContentTypeConnectionID`, AAD собирается через `cryptobyte` вместо
    статического массива — замер клиента: **−11% времени, −48% аллокаций на
    пакет** без CID;
  - по DTLS 1.2 CID-negotiation: **если клиент не посылает расширение CID в
    ClientHello, сервер СБРАСЫВАЕТ И СВОЙ CID** (комментарий ссылается на
    `flight0handler.go-112` библиотеки pion) — то есть объявленный
    шлюзом `RandomCIDGenerator(8)` сегодня **фактически не используется**,
    потому что клиент не даёт согласия. Правка названа «чисто клиентская»:
    шлюз никто не трогал.

  **Практическое следствие для независимого клиента**: реализовывать CID НЕ
  нужно и даже вредно (лишние накладные без выгоды на этом стеке) — сервер
  готов согласовать его, если независимый клиент его предложит, но
  сегодняшний официальный клиент сознательно этого не делает, и повторять
  чужую (не нашу) реализацию транспорта заново не требуется для совместимости.

# ЧАСТЬ B. Релейный путь через VK

## B.0 Устройство в целом — два независимых слоя

Важно разделить сразу, иначе вопросы путаются: «VK» в этой системе даёт
ТОЛЬКО TURN-релей (обход NAT/файрвола через чужую инфраструктуру), а
собственно наш прикладной протокол (GETCONF для WG-режима, AUTH для RAW —
см. первый документ) идёт ПОВЕРХ уже установленного TURN-канала, VK его
содержимого не видит и в нём не участвует. Получение TURN-креды через VK —
это отдельный, самодостаточный шаг ДО открытия сессии к нашему серверу/шлюзу.

## B.1 GETCONF — полный формат (протокол к `wdtt-server`, WG-режим)

Это не «пакет к VK» — это сообщение поверх уже установленного через TURN-
релей DTLS-соединения до `wdtt-server` (боевой сервер,
`/root/wdtt-src/app/src/main/assets/linux-server/`), тот же класс
сообщения, что AUTH в RAW, только для получения WireGuard-конфига, а не
адреса в туннеле напрямую. Вызывается из `RunSession`
(`session.go`, `conf, confErr := RequestConfig(dtlsConn, localPort,
deviceID, password)`) — то есть буквально следующий шаг после того, как
TURN-аллокация и DTLS-хендшейк через релей уже готовы.

**Запрос** (`protocol.go-15`, функция `RequestConfig`):
```
GETCONF:<localPort>|<deviceID>|<password>
```
Текст, один `Write`, без длины/заголовка. `localPort` — локальный UDP-порт
клиента (тот, что клиент слушает под WireGuard, передаётся как строка).

**Ответ** — один `Read` с дедлайном **45 секунд** (`protocol.go`),
буфер 4096 байт (`protocol.go`). Три формы:
- `NOCONF` — точная строка, означает «конфига для тебя нет»;
  `RequestConfig` в этом случае возвращает `("", nil)` — не ошибка
  (`protocol.go-30`);
- `DENIED:<reason>` — отказ, `reason` разбирается строго тремя значениями,
  всё прочее падает в `default` (`protocol.go-43`):
  | `reason` | что видит вызывающий |
  |---|---|
  | `wrong_password` | `FATAL_AUTH: неверный пароль подключения` |
  | `expired` | `FATAL_AUTH: срок действия пароля истёк` |
  | `device_mismatch` | `FATAL_AUTH: пароль привязан к другому устройству` |
  | что угодно ещё | `FATAL_AUTH: доступ запрещён (%s)` с этим reason подставленным |
- любой другой текст — сам конфиг (предположительно текст WireGuard-конфига
  целиком; сам формат конфига этим заходом не разбирал построчно — не
  требовалось для ответа на вопрос про GETCONF как таковой).

Отдельно, рядом в том же файле — `SendAuth` (`protocol.go-57`),
`AUTH:<deviceID>|<password>` — **другой** командный протокол, не связанный
с RAW-блоковским AUTH из первого документа (разный префикс `AUTH:` с
двоеточием против `AUTH|` с чертой, разный набор полей). Найден caller и
разобрано соотношение с GETCONF (`session.go-379`): это **не
последовательность одна-за-другой, а взаимоисключающая ветка внутри одного
воркера** — `RequestConfig`/GETCONF шлёт ТОЛЬКО тот воркер, которому
поручена доставка WG-конфига (`getConfig && configCh != nil`, конкретно
первый свободный в первой группе, см. B.2); **все остальные воркеры группы
вместо этого шлют `SendAuth`** (`session.go-379`) — просто представляются
серверу по DTLS-соединению без запроса конфига, чтобы сервер знал о
существовании этой сессии/устройства. Оба сообщения идут по РАЗНЫМ
DTLS-соединениям (у каждого воркера своё), а не друг за другом по одному.

## B.2 Модель воркеров

**Один хеш = одна группа из 9 воркеров, использующих ОДНИ креды** (не 9
разных TURN-аллокаций с разными кредами — 9 воркеров группы делят один
результат `GetCreds`):
```go
const workersPerGroup = 9   // group.go
```
Комментарий дословно: «Запускает 9 потоков с одними кредами. Ротации нет —
работает до смерти воркеров» (`group.go-18`).

**Общее число воркеров** — из флага (запрошенная «мощность», условно
`-n`), клэмпается тремя правилами по порядку (`main.go-306`):
1. жёсткий потолок `maxWorkers = 108` (`main.go`);
2. если `-vk-auth account`: клэмп до `accountMaxWorkers = 4`
   (`main.go-290`) — «TURN-квота ~4 relay на сессию» у одного VK-аккаунта;
3. иначе (`anonymous`, умолчание): снизу — не меньше `workersPerGroup=9`
   (`main.go-304`), затем округление ВНИЗ до кратного 9
   (`main.go`: `*numW = (*numW / workersPerGroup) * workersPerGroup`) —
   то есть в анонимном режиме число воркеров всегда кратно девяти.

**numGroups** = `ceil(numW / workersPerGroup)` (`main.go`).

**Формула выбора хеша под сессию (группу)** — прямая, без случайности:
```go
hash := tp.Hashes[hashIndex%len(tp.Hashes)]    // group.go
```
где `hashIndex` — это **номер группы** (0-based), переданный как
`startHashIndex` из цикла групп в `main.go` (`startIdx := g *
workersPerGroup`, но конкретно в вызов `WorkerGroup` идёт именно `g`, не
`startIdx` — `main.go`, шестой параметр вызова замыкания — `g`). То
есть **группа №g использует хеш `hashes[g % len(hashes)]`**: если групп
больше, чем хешей, хеши переиспользуются по кругу — несколько групп по 9
воркеров каждая делают СВОИ независимые вызовы `GetCreds` по ОДНОЙ и той же
ссылке (каждый вызов — отдельный «износ» ссылки, см. `noteHashUse`,
`group.go`).

**Каскадный запуск групп**: группа `g+1` ждёт сигнала от группы `g`
(канал `waitReady`/`signalReady`, `group.go-44`), сигнал подаётся через
**2 секунды** после успешного получения кредов группой `g`
(`group.go-128`, `time.Sleep(2000*time.Millisecond)` затем
`close(signalReady)`) — не сразу, чтобы дать группе закрепиться. Внутри
группы воркеры стартуют с шагом **500 мс** (`group.go-134`,
`workerDelay := time.Duration(i) * 500 * time.Millisecond`) — «лесенка» в
старом VPN/WG-пути устроена именно так, в отличие от RAW-многослота
(Часть C), где паузы нет вовсе.

**Обновление кредов посреди сессии**: `refreshCreds` (`group.go-119`),
не чаще раза в **15 секунд** (`group.go-96` — троттлинг повторных
попыток), новый вызов `GetCreds` считается как ещё один «износ» хеша
(`group.go`). Срабатывает по трём классам сетевых ошибок
(`group.go-197`): `TURN Allocate ... attribute not found`, `turn
allocate auth`/`invalid credential`/`stale nonce`/`allocation mismatch`/
`error 508`; отдельно `quota`/`486` — это НЕ повод обновлять креды, а повод
просто ждать дольше (`group.go-191, 241-244`: обычный retry 5-15с,
`quotaRetry` — 30-60с).

## B.4 Проверка живости — `-check-hashes`, формат `HASH_CHECK`

Запускается флагом `-check-hashes` (`main.go`), функция
`runHashChecks(ctx, hashes)` (`main.go-79`). Вывод — **в stdout процесса**
(это протокол управления с внешним драйвером — панелью/ботом/Android-
обвязкой, — не сетевой протокол):

```
HASH_CHECK_START|<номер с 1>|<хеш>
HASH_CHECK|<номер с 1>|<хеш>|<статус>|<сообщение>
```
(`main.go,78`)

Каждая проверка — **полный цикл `GetCreds`** с таймаутом **90 секунд**
(`main.go`), отдельный `streamID = 9000+i` (отдельное адресное
пространство от боевых `groupID*100`, `main.go`). Успешная проверка
**считается использованием хеша** (`noteHashUse`, `main.go`) — «проверка
ссылки кнопкой в панели — тоже полный цикл VKCalls, то есть настоящий
износ» (комментарий `main.go-69`).

| статус | условие (подстрока в тексте ошибки, регистронезависимо) | сообщение |
|---|---|---|
| `ok` | `err == nil` | `TURN urls=%d` |
| `captcha` | `captcha_required` или `captcha_wait_required` | `VK просит капчу` |
| `dead` | `call not found` / `joinconversationbylink` / `missing turn_server` / `9000` / `callunavailable` | `Звонок не найден или закрыт` |
| `limited` | `flood` / `rate limit` / `error_code:29` | `VK временно ограничил запросы` |
| `network` | `timeout` / `deadline` / `lookup` / `network` | `Сетевая ошибка` |
| `error` | всё остальное | текст самой ошибки |

Сообщение (`message`) очищается перед печатью
(`sanitizeHashCheckMessage`, `main.go-113`): переносы строк и `\r`

обрезка до **180 символов**.

## B.5 `-vk-auth anonymous` против `account`

Переключатель — атомарное глобальное значение (`vk_account.go,51-58`),
умолчание `"anonymous"` (`vk_account.go`; любое значение кроме
буквального `"anonymous"` нормализуется в `"account"`, `vk_account.go-54`
— то есть опечатка в значении флага молча трактуется как `account`, не как
отказ разбора, в отличие от большинства других настроек в этом дереве, где
непонятное значение — явный лог и откат к умолчанию).

**Что меняется на проводе — принципиально разное:**

- **`anonymous`** (умолчание): Go-клиент **сам** делает всю цепочку HTTP-
  запросов к VK/OK (см. B.6) и получает TURN-креды без участия
  человека/аккаунта. Лимит воркеров — до `108` (общий потолок), кратно 9.
- **`account`**: Go-клиент **ничего сам не запрашивает** у VK — вместо
  этого печатает в stdout `VK_AUTH_REQUIRED|<link>` (`vk_account.go`) и
  ждёт до **5 минут** (`vk_account.go`) строку `TURN_CREDS|<link>|<base64
  JSON>` на STDIN, разбираемую `handleTurnCredsStdinLine`
  (`vk_account.go-186`): `base64`-тело — JSON вида
  `{"u":"...", "p":"...", "urls":[...]}` (`turnCredsPayload`,
  `vk_account.go-29`). Это значит: реальный вызов VK API в режиме
  `account` делает ВНЕШНИЙ процесс (Android-обвязка приложения,
  предположительно через настоящую авторизованную VK-сессию пользователя) —
  Go-бинарь только передаёт запрос/ответ через свои стандартные потоки.
  Полученные креды кэшируются на **9 минут** (`accountCredsLifetime =
  9 * time.Minute`, `vk_account.go`), по ссылке (`injectedCredsByLink`,
  `vk_account.go-39,93-107`). Лимит воркеров жёстко **4**
  (`accountMaxWorkers`, `main.go`) — «TURN-квота ~4 relay на сессию» у
  одного авторизованного аккаунта VK, кратности 9 в этом режиме нет вовсе
  (клэмп на 9 применяется только в ветке `else`, то есть только для
  `anonymous`, `main.go-306`).
  Есть и статический путь загрузки кредов из файла — `loadVkCredsFile`
  (`vk_account.go-151`), JSON `{"hashes": {"<link>": {"u":..,"p":..,
  "urls":[..]}}}` — судя по месту, для тестового/пакетного впрыска кредов
  без ожидания интерактивного ответа. `[вывод, не проверено]` кем и когда
  вызывается на практике — не проследил caller.

**Требуется от клиента для `account`**: способность держать stdin/stdout
как управляющий канал с внешним драйвером и физически иметь тот
авторизованный VK-аккаунт (или доступ к нему), от лица которого драйвер
делает вызов. Независимый клиент без такой Android-обвязки реализовать
`account`-режим не сможет буквально так же — ему нужен либо свой способ
получить TURN-креды авторизованным VK-запросом, либо ограничиться
`anonymous`.

## B.6 `-vk-anon-path vkcalls|legacy`

Тоже атомарное глобальное значение, умолчание `"vkcalls"`
(`vk_account.go,78-84`; `"legacy"` — единственное распознаваемое
отклонение, всё остальное трактуется как `"vkcalls"`,
`vk_account.go-75`).

Разбор происходит в `fetchVkCreds` (`creds.go-324`):

  (`creds.go-321`, лог `"VK Calls path failed (...), falling back to

себя чинит откатом при неполадке, кроме подтверждённой смерти хеша);

# ЧАСТЬ C. Лестница

## C.1 Полный список кандидатов транспорта и порядок перебора

Собирается функцией `rawCandidates(choice, peer)` (`session_raw_path.go-425`).
При `choice == transportAuto` (умолчание) — это **прямые кандидаты, потом
релейные**, в фиксированном порядке (`session_raw_path.go`:
`return append(directs, relays...)`):

1. **Прямой, без DTLS** (`session_raw_path.go-405`) — ТОЛЬКО если
   `rawDirectNoTLS==true` (по умолчанию `false`, см. первый документ, 2.5).
   Адрес: `<host из -peer>:<rawNoTLSPort>` (умолчание порта `56005`).
2. **Прямой, порт 443** (`session_raw_path.go`, `directPrimaryPort=443`,
   с DTLS) — «этот порт разрешён почти везде» (комментарий
   `session_raw_path.go-296`). Пробуется ВСЕГДА (не за настройкой).
3. **Прямой, порт из `-peer`** (`session_raw_path.go-409`) — только
   если `peer.Port != 0 && peer.Port != 443` (обычно это `56004`, если
   `-peer host:56004`). С DTLS.
4. **Релей, без DTLS** (`session_raw_path.go-397`) — ТОЛЬКО если
   `rawRelayNoTLS==true` (по умолчанию `true` с 3.7). Через TURN-релей на
   `<host шлюза>:<rawNoTLSPort>`.
5. **Релей, с DTLS** (`session_raw_path.go-386`) — пробуется ВСЕГДА,
   последний в списке, «тот же самый годами» вариант.

При `choice == transportDirect` — возвращаются ТОЛЬКО пункты 1-3 (без
отката на релей вообще, `session_raw_path.go-417`). При `choice ==
transportRelay` — только 4-5 (`session_raw_path.go-414`). `choice`
берётся из `-transport` флага, иначе `TRANSPORT` в конфиге, иначе
`"auto"` (`resolveTransportChoice`, `session_raw_path.go-243`).

## C.2 Условия перехода к следующему кандидату и таймауты

Цикл перебора — `session_raw.go-686` (уже цитировался в контексте
поколения сессии, здесь — по сути перехода):

```go
for _, cand := range cands {
    lk, attErr := dialCandidate(cand, ctx, rawAuthCaps(sessionGen))
    if attErr == nil { link = lk; break }               // успех — стоп
    if errors.Is(attErr, errFatalAuth) { return attErr } // пароль неверен — стоп ВСЕГО, не только кандидата
    // иначе — лог и переход к следующему кандидату
}
```

**Любая ошибка кандидата, КРОМЕ `errFatalAuth`, ведёт к следующему
кандидату немедленно** — TURN-аллокация не встала, DTLS-хендшейк не
прошёл, AUTH не ответил вовремя, ответ AUTH синтаксически неверный — всё
это одинаково «кандидат не поднялся, пробуем следующий». **`errFatalAuth`
(неверный пароль) обрывает ВЕСЬ перебор сразу** — ни один из оставшихся
кандидатов даже не пытается: пароль один на все пути, значит и остальные
провалятся тем же образом (комментарий `session_raw.go-160`).

**Таймауты — по кандидату**, заданы в `rawCandidate.handshakeTimeout` и
`.authTimeout` (`session_raw_path.go-425`):

| кандидат | handshakeTimeout | authTimeout |
|---|---|---|
| прямой (443, порт из peer, notls) | **6 с** (`session_raw_path.go`) | **8 с** (`session_raw_path.go`) |
| релей с DTLS | **50 с** (`session_raw_path.go`) | **15 с** (`session_raw_path.go`) |
| релей без DTLS | не применим (рукопожатия нет) | **8 с** (`session_raw_path.go`, специально снижен с 15 — «за нами стоит рабочая страховка») |

`handshakeTimeout` используется как таймаут DTLS-рукопожатия
(`session_raw.go`, `context.WithTimeout(sessCtx,
cand.handshakeTimeout)`); `authTimeout` — как дедлайн чтения ответа на AUTH
(`session_raw.go`, см. первый документ 1.2).

## C.3 Неудача кандидата против повторной попытки того же кандидата

**Внутри одного вызова `RunRawSession` каждый кандидат пробуется РОВНО ОДИН
раз.** Нет отдельной логики «повторить тот же кандидат N раз перед
переходом к следующему» — единственная попытка, любая ошибка = переход
дальше по списку (C.2). Единственное исключение —**динамические слоты**
(C.5, автоподбор): там повторный дозвон ТОГО ЖЕ кандидата (`link.cand`) в
рамках уже идущей сессии — это не «повтор неудачного кандидата», а
открытие ДОПОЛНИТЕЛЬНОГО слота поверх уже успешно поднятого пути.

Повтор ЦЕЛОГО кандидата после провала происходит только на СЛЕДУЮЩЕМ
запуске `RunRawSession` — то есть на следующей сессии, когда список
`cands` строится заново с нуля (`session_raw.go`, `cands :=
rawCandidates(...)`) и перебор снова стартует с пункта 1.

## C.4 Переход односторонний, или возврат на верхнюю ступень — оба механизма есть, разные по природе

**Механизм 1 — «переезд» (proactive), работает ТОЛЬКО находясь на резервном
пути внутри ОДНОЙ живой сессии** (`session_raw.go-772`, уже разобран в
первом документе как «тихая перепроверка»; здесь — детали таймингов из
`session_raw_path.go`, не описанные в первом заходе):

- условие запуска: `!link.cand.isDirect() && rawTransportChoice ==
  transportAuto && rawDirectRecheck > 0` (`session_raw.go`) — то есть
  ТОЛЬКО в автоматическом режиме и только если перепроверка не выключена
  (`DIRECT_RECHECK=0`);
- проверяет **только порт 443** прямого пути (`directProbeAddr`,
  `session_raw_path.go-591`) — если у клиента закрыт именно 443, но
  открыт 56004/56005 прямого пути, «переезд» этого не увидит вовсе
  (честно задокументировано, `session_raw_path.go-513`);
- проба — не настоящий дозвон, а обмен `QWDTT-PROBE:<12 случайных байт>`
  (`probeDirectPayload`, `session_raw_path.go-511`) с ожиданием
  точного эха от шлюза (шлюз отвечает на неё ДО DTLS, см. Часть A/1
  первого документа, `main.go-512`) — не задевает живую сессию,
  занятый по паролю слот на шлюзе не трогает;
- интервал — `rawDirectRecheck` (умолчание **15 минут**, `DIRECT_RECHECK`
  в конфиге), с экспоненциальным откатом при «вранье пробы» (см. ниже);
- при успешной пробе: сессия **штатно завершается СВОИМ решением**
  (`sessCancel()`, `session_raw.go`) — это НЕ смена транспорта на
  лету, а управляемый обрыв текущей сессии, после которого внешний
  retry-цикл (`main.go`) стартует НОВУЮ сессию, и уже её `cands`-список
  (C.1) естественно начнётся с прямых кандидатов.

**Защита от «проба соврала»** — `directFailStreak`
(`session_raw_path.go-568`): если сессия, начатая ПРЯМЫМ кандидатом
ПОСЛЕ переезда, тем не менее не встаёт по-настоящему, счётчик растёт, и
следующая проба откладывается по формуле `nextRecheckDelay(base, fails) =
base * 2^min(fails,3)` (`session_raw_path.go-582`) — то есть 15, 30,
60, 120 минут (потолок — восьмикратная база), сбрасывается в ноль при
первом же успешном прямом старте (`session_raw.go-668`).

**Механизм 2 — `decideStartPath`, работает на ГРАНИЦЕ каждой сессии, а не
только сидя на резервном пути** (`session_raw_path.go-655`,
вызывается из `main.go`, **до похода в VK**):

- при `TRANSPORT=direct`/`relay` — решение задано настройкой, проба не
  нужна (`session_raw_path.go-633`);
- при `auto` (умолчание) — короткая проба тем же `QWDTT-PROBE` с
  таймаутом всего **2 секунды** (`startProbeTimeout`,
  `session_raw_path.go`) на порт 443. Отвечает — сессия стартует
  СРАЗУ прямым путём, **минуя поход в VK вообще** (`session_raw_path.go-650`,
  `directFirst=true`, применяется в `main.go-443`: `maybeWarmCreds`
  вместо немедленного `GetCreds`); не отвечает — как раньше, сначала VK,
  потом кандидаты по списку (`session_raw_path.go-654`);
- есть защита от «раз проба сказала можно, а сессии всё равно рвутся
  быстро» — `quickFails` (описан в C.2 выше в контексте `directFailStreak`
  но это ОТДЕЛЬНЫЙ счётчик, `main.go`): если ≥`directQuickFailLimit=2`
  подряд сессий, начатых сразу прямым путём, развалились быстрее
  `directQuickFailWindow=30с`, на следующем старте `decideStartPath`
  игнорирует успешную пробу и всё равно идёт сначала за VK-кредами
  (`session_raw_path.go-641`) — «резерв должен быть настоящим».
  Счётчик обнуляется по ЛЮБОЙ сессии, прожившей ≥30с, независимо от того,
  как она стартовала (`main.go-489`, специально, чтобы не залипнуть в
  недоверии навсегда).

**Итог: переход НЕ односторонний.** Возврат на верхнюю ступень (прямой
путь) происходит по ДВУМ независимым, живым (не по конфигу) событиям:
успешная тихая проба во время сессии (Механизм 1) или успешная короткая
проба на старте следующей сессии (Механизм 2, срабатывает даже если
Механизм 1 выключен или ждёт своих 15 минут).

## C.5 Автослоты — по какому признаку, снятие, пороги

Контроллер `autoSlots` (`session_raw_autoslots.go-524`) — измеряет
раз в окно **60 секунд** (`slotWindow`, `:319`) простой ядер CPU (из
`/proc/stat`, дельта idle/total между чтениями) и объём принятого трафика
за окно, и по этим двум числам решает `+1`/`0`/`-1` слот. Живёт МЕЖДУ
сессиями (переживает их смену, `session_raw_autoslots.go`
`autoSlotsCtl — контроллер живёт МЕЖДУ сессиями, а не внутри одной`), но
рост/снятие слота применяется **прямо внутри текущей сессии** (не только
на границе следующей — это подтверждено кодом `addSlot`/`startAutoSlots`,
`session_raw.go-1270`, комментарий там же: «нужен способ поднять слот
на ходу — иначе решение о росте живёт в состоянии, а раздача остаётся
прежней»).

**Полная таблица порогов** (`session_raw_autoslots.go-321`):

| константа | значение | что делает |
|---|---|---|
| `slotWindow` | 60 с | длина окна наблюдения |
| `idleShrinkCores` | 0.25 ядра | простоя МЕНЬШЕ этого → снять слот НЕМЕДЛЕННО (одно окно, без подтверждения) |
| `idleGrowCores` | 0.7 ядра | простоя БОЛЬШЕ этого нужно, чтобы вообще начать считать окна для роста |
| `growWindows` | 2 | столько ПОДРЯД «здоровых» окон (простой ≥0.7, не на потолке, не в заморозке) нужно для решения о росте |
| `minWindowBytes` | 200 КБ/окно | меньше — трафика нет, не растим, что бы ни говорил простой |
| `gainWindows` | 3 | сколько окон ДО и ПОСЛЕ добавления слота собирается для оценки окупаемости (по МЕДИАНЕ, не одному окну) |
| `minGainFraction` | 5% | прирост полосы медианой после/до меньше этого → «потолок сети», заморозка роста |
| `frozenRetry` | 15 мин | через сколько заморозка сама снимается и рост пробуется снова |
| `frozenBandJump` | 1.5× | если полоса выросла БОЛЬШЕ этого — заморозка снимается ДОСРОЧНО, не дожидаясь таймера |
| `shrinkLock` | 5 мин | после снятия слота рост запрещён это время (защита от маятника) |
| `defaultSlotsMax` | 8 | потолок автоподбора по умолчанию (СВОЙ, отдельный от протокольного `maxRawSlots=9` из первого документа) |

**Снятие слота** — есть, и оно быстрее роста намеренно (асимметрия
подтверждена комментарием `session_raw_autoslots.go-269`: «расти
медленно — два окна подтверждения, снимать быстро — одно окно»): один
момент с простоем `<0.25` ядра → снять слот немедленно, без подтверждения
вторым окном. Снимается всегда ПОСЛЕДНИЙ добавленный (`slotSet.last()`,
первый документ, 3.х), не случайный.

**Условие применимости вообще** (`autoSlotsApplies`,
`session_raw_autoslots.go-780`): включён `SLOTS_AUTO`/`-slots-auto`
(умолчание — **выключено**), путь НЕ прямой («на прямом пути нет шейпа на
аллокацию, наращивать нечего»), шлюз подтвердил `multi` в AUTH — те же три
условия, что у статического многослота в первом документе.

## C.6 Что из конфига, что решается на лету

| настройка | ключ конфига / флаг | умолчание | входит в «лестницу» как |
|---|---|---|---|
| выбор транспорта | `TRANSPORT` / `-transport` | `auto` | при `auto` — решается ЖИВОЙ пробой на каждом старте сессии (C.4, Механизм 2); при заданном значении — статический выбор без проб вообще |
| DTLS на релее | `RELAY_NOTLS` / `-relay-notls` | `1` (включено, с 3.7) | СТАТИЧЕСКИЙ переключатель — не адаптируется к условиям, только к явной настройке (см. C.7) |
| DTLS на прямом пути | `DIRECT_NOTLS` / `-direct-notls` | `0` (выключено) | тот же СТАТИЧЕСКИЙ переключатель, ручной |
| порт notls-путей | `DIRECT_NOTLS_PORT` / `-direct-notls-port` | `56005` | статика |
| интервал тихой перепроверки | `DIRECT_RECHECK` / `-direct-recheck` | 15 мин | сам интервал — конфиг; СРАБАТЫВАНИЕ внутри интервала — живая проба |
| базовое число слотов | `SLOTS` / `-slots` | `min(4, ядер)` | статический расчёт по числу ядер РАЗ при старте процесса, не адаптируется сам, если явно не задан |
| автоподбор слотов | `SLOTS_AUTO` / `-slots-auto` | **выключен** | сам механизм ПОЛНОСТЬЮ живой (C.5), но ВКЛЮЧЕНИЕ его — статический флаг |
| потолок автоподбора | `SLOTS_MAX` / `-slots-max` | 8 | статика |
| упреждающая ротация | `ROTATE_AFTER` / `-rotate-after` | `0` (выключена) | чистая статика по таймеру, никакой адаптации к условиям канала |

## C.7 Чего не хватает, чтобы лестница решалась ПОЛНОСТЬЮ на лету — ключевой вопрос части C

Разделяю на два разных класса, потому что ответы разного типа.

**А. Уже полностью на лету, без конфига, сегодня** (мобильному приложению
для этого не нужен файл конфига — можно передавать флагами напрямую из
кода приложения, а можно вообще не передавать, умолчания разумны):
- выбор прямой/резервный путь при `TRANSPORT` не заданном — живая проба
  каждый старт (C.4);
- «переезд» обратно на прямой путь, сидя на резервном (C.4, Механизм 1);
- самокоррекция «проба лжёт» — оба счётчика (`directFailStreak`,
  `quickFails`) не требуют настройки вовсе, работают из коробки;
- если `SLOTS_AUTO` включить (одним флагом, без файла) — весь дальнейший
  подбор числа слотов полностью адаптивный (C.5).

**Б. Не хватает — то, что сегодня требует РУЧНОГО решения, а не измеряется
само:**

1. **Включённость `DIRECT_NOTLS` и `RELAY_NOTLS` — не результат
   измерения, а замороженное решение человека.** Особенно
   показательно для `DIRECT_NOTLS`: комментарий прямым текстом говорит
   «ПО УМОЛЧАНИЮ ВЫКЛЮЧЕН и остаётся выключенным, ПОКА ВЛАДЕЛЕЦ НЕ
   ПРОВЕРИТ его на своём роутере» (`session_raw_path.go-64`) — то есть
   это не «решим по факту, работает или нет», а «ждём ручного включения
   навсегда, пока кто-то физически не подтвердит». Мобильному приложению
   без оператора, включающего это вручную на каждом устройстве, не
   хватает **пробы прямого-без-DTLS так же, как есть проба прямого-с-DTLS**
   (та же `QWDTT-PROBE`/эхо-механика технически позволяет это — probe на
   443 сегодня не различает, ответил ли DTLS-путь или notls-путь).
2. **Перепроверка (`decideStartPath`/переезд) видит ТОЛЬКО порт 443.**
   Если у клиента закрыт именно 443 (а не 56004/56005), лестница не узнает
   о доступности прямого пути на других портах до следующей ПОЛНОЙ смены
   сессии, где кандидаты перебираются взаправду. Не хватает: пробы на
   ВСЕ кандидатные адреса/порты, а не только на «главный».
3. **Базовое число слотов (`SLOTS`) — статический расчёт по числу ядер,
   не по факту канала.** Если `SLOTS_AUTO` не включён (умолчание),
   мобильное приложение стартует с `min(4,ядер)` слотами и никогда не
   узнает, нужен ли вообще второй слот, — не хватает **включения
   `SLOTS_AUTO` по умолчанию** (сегодня это отдельный осознанный флаг,
   а не то, что решается автоматически).
4. **`ROTATE_AFTER` — чистый таймер, без обратной связи с состоянием
   канала.** Плановая ротация сегодня либо есть по расписанию, либо её нет
   вовсе; не хватает решения вида «ротировать, когда деградация канала
   ХУЖЕ, чем стоимость самой ротации (полный DTLS-хендшейк + простой)»,
   а не по фиксированному времени.
5. **Самое общее: ни один из полностью живых механизмов (проба на 443,
   автослоты) не расширен на ДРУГИЕ измерения качества канала** —
   например, задержку (RTT) или потери пакетов внутри уже установленной
   сессии, не только на этапе выбора пути. Лестница сегодня решает «какой
   путь поднять», но не «путь поднялся, но он ХУЖЕ другого — стоит ли
   переехать» вне явного разрыва/пробы конкретно порта 443.

**Практический вывод для мобильного приложения без файла конфига**:
приложение может передать флаги напрямую (`-transport=auto` и не трогать
остальное) и получить сегодняшнее поведение парка «из коробки» — файл
`qwdtt.conf` для этого не обязателен, потому что каждая настройка уже
имеет разумное умолчание в коде. Но чтобы лестница была самонастраивающейся
ПОЛНОСТЬЮ (без оператора, решающего когда-то один раз «включить
DIRECT_NOTLS»), не хватает именно того, что перечислено в пункте Б —
это НОВАЯ работа, не просто «убрать чтение файла».
