внесена ни в один файл. Цель: описать протокол так, чтобы по описанию можно

  диске, дальше всего от боевой сборки, но ближе всего к «как это должно

## Метод

- Каждый факт — `файл:строка`. Без ссылки факт не идёт в документ.
- `[код]` — прочитано в исходнике. `[измерено]` — получено запуском чего-либо
  на этой машине. `[хендофф]` — записано в `/root/*.md` предыдущими сессиями,
  не проверено этим разведом. При расхождении кода и хендоффа — прав код,
  расхождение вынесено в свой раздел.
- `[вывод, не проверено]` — умозаключение поверх прочитанного, не факт сам по
  себе.
- Секреты (пароли, ключи, токены, VK-хеши) нигде не выписаны, только имена
  полей и форматы.

## БЛОК 1. RAW — провод

### 1.1 Слушатели

Шлюз — **только UDP**: `net.Listen("tcp"...)` в дереве шлюза отсутствует
(проверено `grep`, ноль совпадений во всём `main.go`). Три листенера:

| порт (умолчание флага) | флаг | транспорт | код |
|---|---|---|---|
| `56004` | `-listen` | DTLS/UDP, **безусловно поднимается** (нет проверки на пустоту флага) | `main.go`, запуск `main.go` |
| `443` | `-listen-direct`, умолчание `"0.0.0.0:443"` | DTLS/UDP, поднимается если флаг не пуст (пуст по умолчанию — не бывает: умолчание непустое) | `main.go`, запуск `main.go-1353` |
| выключен по умолчанию (`""`) | `-listen-notls` | **без DTLS**, obfs прямо поверх UDP-сокета | `main.go`, запуск `main.go-1356` |

`[измерено]` **Живой процесс на этой машине** (`ps`, `systemctl cat
raw-gateway`) запущен флагами `-listen 0.0.0.0:56004 -listen-notls
0.0.0.0:56005 -config-dir /etc/wdtt -tun-name qwdttraw0 -tun-cidr
10.77.77.1/24` — `-listen-direct` не передан, значит действует умолчание
`443`. То есть на этом шлюзе реально слушаются **три** порта: `56004` (DTLS,
через TURN-релей), `443` (DTLS, прямой путь, умолчание флага), `56005`
(без DTLS, прямой путь, порт явно задан).

`56004` обслуживает клиентов, пришедших через TURN-аллокацию VK-релея; `443`
— тех же клиентов «напрямую», без релея. Разницы в обработке на шлюзе НЕТ:
«для шлюза прямой клиент отличается только адресом источника — логика та же»
(`main.go-1347`).

### 1.2 AUTH

Формат сообщения (текст, не бинарь, разделитель `|`), задан и на клиенте, и
на шлюзе идентично:

```
AUTH|<password>|<device_id>|<caps>
```

- Клиент собирает и шлёт: `authMsg := fmt.Sprintf("AUTH|%s|%s|%s", password,
  deviceID, caps)` — `session_raw.go`. Если `caps==""`, подставляется
  `"echo"` (`session_raw.go-145`).
- Шлёт клиент ПЕРВЫМ, сразу после установления транспорта (DTLS-хендшейка
  или, на прямом пути без DTLS, сразу после открытия UDP-сокета) —
  `session_raw.go` вызывается сразу в начале `rawAuthenticate`.
- Шлюз читает как один `Read` с дедлайном 20 с: `dtlsConn.SetReadDeadline(...
  20*time.Second)`, `dtlsConn.Read(buf)` — `main.go-1201`. Буфер
  `readBufSize+80` байт, `readBufSize=1600` (`main.go`), т.е. до 1680 байт.
- Разбор: `strings.SplitN(authStr, "|", 4)` — **максимум 4 части**, четвёртая
  (`caps`) может содержать `|` внутри себя, если бы он там был (сегодня не
  используется) — `main.go`.
- Валидность: `len(parts) < 3 || parts[0] != "AUTH"` → отказ (`main.go`).
  **На синтаксически негодный AUTH шлюз НЕ отвечает вообще** — просто
  `log.Printf` и `return`, соединение закрывается через `defer
  dtlsConn.Close()` (`main.go, 1196`). Ответ `FATAL_AUTH` шлётся только
  на СИНТАКСИЧЕСКИ ВАЛИДНЫЙ AUTH с неверным содержимым:
  - неверный/истёкший пароль (`checkPassword` вернул false) →
    `dtlsConn.Write([]byte("FATAL_AUTH"))` — `main.go-1241`;
  - пул адресов исчерпан (`assignClientIP` вернул ошибку) → тот же ответ —
    `main.go-1250`.
  Клиент проверяет строго по префиксу: `strings.HasPrefix(resp,
  "FATAL_AUTH")` → возвращает `errFatalAuth`, **не перебирает остальных
  кандидатов транспорта** (`session_raw.go-160`, комментарий: «пароль
  один на всех путях: перебирать остальные бессмысленно»).
- Четвёртое поле `caps` — набор через запятую: `echo`, `multi`,
  `gen=<токен>` (подробнее в 1.5 и Блоке 3). Шлюз матчит подстрокой
  (`strings.Contains`), не точным разбором списка, кроме `gen=` — та достаётся
  явным разбором по `,` (`main.go-1163`, функция `authGeneration`).

### 1.3 Ответ на успешный AUTH

Текст, `|`-разделитель:

```
OK|<assigned_ip>|<gateway_ip>|<netmask>[|<caps>]
```

Собирается на шлюзе: `okMsg := "OK|" + clientIP.String() + "|" +
g.tunCIDR.IP.String() + "|" + g.tunCIDR.Mask.String()` — `main.go`.

- поле 2 — выданный клиенту адрес в туннеле;
- поле 3 — адрес самого шлюза в этой подсети (у нас `10.77.77.1`,
  `-tun-cidr`);
- поле 4 — маска подсети. **⚠️ Формат — `net.IPMask.String()` в Go, это
  ХЕКС-строка (`"ffffff00"`), НЕ точечно-десятичная запись
  (`"255.255.255.0"`)**. Кто пишет независимый клиент на другом языке, обязан
  разобрать именно так — это частое место ошибки при переносе;
- поле 5 (опционально, если `caps` непусто) — подтверждённые сервером
  возможности через запятую: `echo`, `multi`, `gen` — собирается на
  `main.go-1279`. Присутствие подстроки в этом поле — это ПОДТВЕРЖДЕНИЕ
  сервером соответствующей возможности клиента, а не эхо запроса дословно
  (сервер конструирует поле заново).
- **Ни DNS, ни MTU в ответе НЕТ.** Проверено grep по обоим деревьям —
  `assignClientIP`/`okMsg` не содержат таких полей (`main.go-1280`
  целиком). MTU — на обеих сторонах отдельная константа `1200`, задаётся не
  протоколом, см. 1.6. DNS в RAW-режиме клиентом на этом уровне не
  запрашивается вовсе (`grep DNS` по `session_raw.go`/`main.go` клиента пуст,
  кроме несвязанного `setupGlobalResolver` в общем DoH-коде,
  `main.go` клиента — к RAW-сессии отношения не имеет).

Клиент разбирает ответ: `strings.Split(resp, "|")`, требует
`len(parts)>=4 && parts[0]=="OK"` (`session_raw.go-164`); `parts[1]` —
присвоенный IP, `parts[2]`/`parts[3]` в лог, но нигде дальше в код не
используются как параметры сети (`session_raw.go` — только печать в лог);
адрес шлюза и маска клиенту, судя по коду, для дальнейшей настройки TUN не
нужны — TUN поднимается отдельно с фиксированными параметрами (см. 1.6).

### 1.4 Назначение адреса — по хешу пароля, не устройства

Подтверждено по коду. `device_id` из AUTH используется ТОЛЬКО в логах
шлюза (`main.go`, `1286-1288`) и нигде в вычислении адреса не участвует
(в `assignClientIP` параметр `password`, не `deviceID` — `main.go`).

```go
func preferredSlot(password string) byte {           // main.go
    var h uint32
    for i := 0; i < len(password); i++ {
        h = h*31 + uint32(password[i])
    }
    return byte(h%ipSlotCount) + ipSlotFirst
}
```

`ipSlotFirst=2`, `ipSlotCount=253` (`main.go-196`) — слоты `.2`…`.254`
внутри `/24` из `-tun-cidr` (`.0` — сеть, `.1` — сам шлюз, `.255` —
broadcast).

**Поведение при коллизии двух устройств с одним хешем** (`main.go-280`,
функция `assignClientIP`):
- раскладка каждый раз считается заново по ВСЕМУ множеству паролей из
  `passwords.json` (не по порядку подключения);
- при конфликте предпочтительного слота приоритет — у
  **лексикографически меньшего пароля**; проигравший линейно ищет следующий
  свободный слот по кольцу (`(want-2+i)%253+2`);
- событие логируется явно: `"слот %s занят, пароль уступает по канону —
  выдаю %s"` (`main.go-251`);
- **уже выданный живому клиенту адрес не переигрывается никогда**, даже если
  по канонической раскладке слот должен принадлежать другому
  (`main.go-267`, `271-273` — сначала проверяется, выдан ли пароль уже,
  такой пропускается в переборе).
- Персистентности на диске нет: адрес каждый раз шлётся клиенту заново в
  ответе AUTH, клиент его не вычисляет сам (комментарий `main.go-192`).

### 1.5 Keepalive и «эхо-keepalive»

**Маркер**: 4 нулевых байта `[]byte{0, 0, 0, 0}` — `session_raw.go`.
Специально невалиден как IPv4-заголовок (первый байт версии/IHL не может
означать 0), чтобы шлюз надёжно отличал его от настоящего пакета.

**Кто шлёт**: клиент, раз в 20 секунд (`time.NewTicker(20 * time.Second)`,
`session_raw.go`), в КАЖДЫЙ живой слот при многослоте
(`slots.writeAll(keepaliveMarker)`, `session_raw.go-991`) плюс основное
DTLS-соединение (`session_raw.go`).

**Что делает шлюз** (`main.go-1122`): если принятый пакет короче 20
байт (`n < 20` — валидный IPv4-заголовок короче быть не может), это
keepalive, не данные:
- отмечает `lastSeen` (уже сделано строкой раньше, `main.go`, ДО
  разбора — молчащий, но живой слот обязан остаться в раздаче);
- если клиент НЕ подтвердил `echo` в AUTH (`!c.echoKeepalive`) — маркер
  просто отбрасывается, ответа нет (`main.go-1119`);
- если подтвердил — шлюз **отправляет тот же маркер обратно** тем же
  сообщением (`c.dtls.Write(buf[:n])`, `main.go`).

**Что означает `echo-keepalive=false` в логе клиента**
(`session_raw.go`, поле `эхо-keepalive=%v`): шлюз НЕ подтвердил
возможность `echo` в ответе AUTH (поле 5 отсутствует или без подстроки
`echo`) — либо старый шлюз, не понимающий это поле вовсе, либо клиент сам не
запросил его. В этом состоянии у клиента **выключена детекция мёртвого
канала по тишине**: `if silence ... && echoConfirmed && silence >
rxSilenceLimit` (`session_raw.go`) — условие проверяется, только если
`echoConfirmed==true`. Без эха клиент не может отличить живую, но простаивающую
сессию от TURN-аллокации, умершей молча (протухшие VK-креды — запись в неё
не возвращает ошибку, `session_raw.go-1004`).

**Обязателен ли echo**: нет, это capability-negotiation, полностью обратно
совместимая (`session_raw.go-141`, `main.go-1225`) — старый клиент
не шлёт `echo`, не получает эхо и не падает; новый клиент со старым шлюзом
не получает подтверждения и просто не включает детекцию.

**rxSilenceLimit** — порог полного молчания входящего потока при
подтверждённом echo: **90 секунд** (`session_raw.go`, `const
rxSilenceLimit = 90 * time.Second`) — «четыре с лишним пропущенных подряд
ответа» при интервале 20 с.

### 1.6 MTU

`[код]` **Не асимметрично сегодня — обе стороны используют одну и ту же
константу 1200, СИММЕТРИЧНО**:
- клиент: `tun.CreateTUN(tunName, 1200)` — `session_raw.go`, число
  зашито прямо в вызов, без именованной константы;
- шлюз: `tunMTU = 1200` (`main.go`), используется при создании TUN
  (`main.go`) и при `ip link set ... mtu 1200` (`main.go`).

MTU протоколом НЕ передаётся (см. 1.3) — это независимая локальная константа
на каждой стороне, совпадение значений сегодня держится на дисциплине, не на
согласовании.

**Расхождение с хендоффом** — см. отдельный раздел ниже, там же разбор, что
именно имелось в виду под «асимметрией».

### 1.7 Обнаружение ухода клиента и таймаут снятия сессии

Шлюз — скользящий дедлайн чтения, переустанавливается перед КАЖДЫМ чтением
(`main.go-1063`):

```go
deadline := clientReadDeadline      // main.go, = 5 * time.Minute (main.go)
if c.multi {
    deadline = multiReadDeadline    // main.go, = 90 * time.Second (main.go)
}
c.dtls.SetReadDeadline(time.Now().Add(deadline))
n, err := c.dtls.Read(buf)
```

- односегментный клиент (`c.multi==false`) — **5 минут** без единого пакета
  (включая keepalive-маркеры — они тоже двигают `lastSeen`/дедлайн);
- многослотовый — **90 секунд** на КАЖДЫЙ слот отдельно (не на сессию целиком
  — у каждого слота своё соединение и свой вызов `clientReaderLoop`).

Других механизмов обнаружения ухода (пинг с шлюза, TCP RST и т.п.) в коде
нет — только истечение дедлайна чтения на конкретном UDP/DTLS-соединении.

## БЛОК 2. Обфускация и криптография (общая часть client/gateway)

Файлы `obfs.go` клиента и шлюза **побайтно идентичны по логике** (сверено
построчно) — общий код скопирован, а не переиспользуется через общий модуль.

### 2.1 Форма пакета — подтверждено

```
[RTP-заголовок 12 байт][ChaCha20-Poly1305: шифротекст+тег 16 байт][паддинг 0..N][PadLen 1 байт]
```
(`obfs.go-10` — идентичный комментарий в обоих деревьях)

Первые 12 байт (`obfsWrapPacket`, `obfs.go-366` шлюза /
`obfs.go-374` клиента — идентично):

| байт(ы) | значение | код |
|---|---|---|
| 0 | `0x80 \| 0x20` = `0xA0` — V=2 (биты 7-6), P=1 (бит 5, есть паддинг), X=0, CC=0 | `out[0] = 0x80 \| 0x20` |
| 1 | Payload Type: `111` (0x6F, audio, умолчание) или `96` (0x60, video); старший бит (marker) всегда 0, `PayloadType & 0x7F` | `out[1] = cfg.PayloadType & 0x7F` |
| 2-3 | Sequence Number, big-endian uint16 | `binary.BigEndian.PutUint16(out[2:4], seq)` |
| 4-7 | Timestamp, big-endian uint32 | `binary.BigEndian.PutUint32(out[4:8], ts)` |
| 8-11 | SSRC, big-endian uint32, случайный на сессию/слот | `binary.BigEndian.PutUint32(out[8:12], cfg.SSRC)` |

Отсюда `0xA0 0x6F` для audio-режима (`0xA0 0x60` для video) — подтверждает
заявленное в задаче `a0 6f`.

**seq/timestamp — не независимые случайные, а детерминированный счётчик от
одного случайного старта** (`ObfsState`, `obfs.go-119` шлюза):
```go
seq := state.initSeq + uint16(c)               // obfs.go (шлюз) / :343 (клиент)
ts  := state.initTs + uint32(c)*960 + uint32(c>>16)   // "960" — шаг таймстампа на пакет (комментарий: "поколение" RTP timestamp, аналог 20мс OPUS-фрейма при 48кГц)
```
где `c` — 64-битный монотонный счётчик пакетов сессии (`state.count`,
инкрементируется под мьютексом на каждый `obfsWrapPacket`,
`obfs.go-333`). `initSeq`/`initTs` — 6 случайных байт при создании
состояния (`NewObfsState`, `obfs.go-111`).

**Что проверяет принимающая сторона при распаковке**
(`obfsUnwrapPacket`, `obfs.go-446` шлюза / идентично клиента):
- версия RTP строго `2` (`(wire[0]>>6) != 2` → отказ) — `obfs.go-408`;
- длина пакета не меньше 13 байт (12 заголовок + ≥1 байт паддинга/данных) —
  `obfs.go-403`;
- если бит P (0x20) установлен — читает последний байт как `padLen`,
  проверяет `padLen != 0 && padLen <= payloadEnd-12` — `obfs.go-423`;
- AEAD-тег через `aead.Open(...)` — криптографическая проверка целостности и
  подлинности заголовка+шифротекста (AAD = сами 12 байт заголовка, см. 2.2).

**Что ИГНОРИРУЕТСЯ принимающей стороной**: PayloadType на приём НЕ
проверяется в `obfsUnwrapPacket` вообще (используется только для детекции
«похоже ли это на наш пакет», `obfsIsRTPPacket`, `obfs.go-462`, где
допустимы оба значения `111`/`96`); marker-бит (бит 7 байта 1) не читается
нигде; поле CC (биты 3-0 байта 0) не проверяется — заголовок жёстко 12 байт,
без CSRC-списка, независимо от значения этих битов на входе (расширение
X и CSRC-список RTP не реализованы и не проверяются).

### 2.2 AEAD ChaCha20-Poly1305 — сборка нонса

```go
// obfsBuildNonceInto, obfs.go-322 (клиент), :309-314 (шлюз)
func obfsBuildNonceInto(n *[12]byte, ssrc uint32, seq uint16, ts uint32) {
    binary.BigEndian.PutUint32(n[0:4], ssrc)
    binary.BigEndian.PutUint16(n[4:6], seq)
    n[6], n[7] = 0, 0
    binary.BigEndian.PutUint32(n[8:12], ts)
}
```

12-байтный нонс = `[SSRC 4Б][Seq 2Б][0x00 0x00][Timestamp 4Б]` — **не то же
самое побайтовое расположение, что у самого RTP-заголовка** (там порядок
`Seq, Timestamp, SSRC`; в нонсе — `SSRC, Seq, padding, Timestamp`).
Единственность нонса на ключ обеспечивается тем, что `(SSRC, seq, ts)`
монотонно и детерминированно растут от случайного старта на весь пакетный
поток сессии (см. 2.1); повторное использование одного нонса при живой
сессии по коду исключено арифметикой счётчика.

AAD (Additional Authenticated Data) в `Seal`/`Open` — сами 12 байт RTP-
заголовка (`aead.Seal(out[12:12], nonce[:], payload, out[:12])`,
`obfs.go`/`obfs.go`; `aead.Open(dst[:0], nonce[:], wire[12:payloadEnd],
wire[:12])`, `obfs.go`/`:429`) — то есть заголовок аутентифицируется, но
не шифруется (что и требуется: DPI должен видеть «нормальный» RTP-заголовок).

Ключ — 32 байта (`wrapKeyLen = 32`, `wrap.go` обеих сторон), из HKDF (2.3).
Шифр кэшируется по ключу (`sync.Map`, `aeadCache`, `obfs.go-42`) — на
сессию создаётся один `cipher.AEAD` (`ObfsState.aead`,
`NewObfsStateWithKey`, `obfs.go-119`/`obfs.go-101`), а не заново на
каждый пакет.

### 2.3 HKDF-SHA256 — точная схема

Идентична на клиенте (`wrap.go`) и шлюзе (`wrap.go` шлюза, сверено побайтно):

```go
func deriveWrapKey(password string) ([]byte, error) {   // wrap.go
    key := make([]byte, 32)                              // wrapKeyLen, wrap.go
    reader := hkdf.New(
        sha256.New,
        []byte(password),              // IKM  — сам пароль подключения, как есть
        []byte("WDTT-WRAP-v1"),        // salt — константа
        []byte("rtp-obfs/chacha20poly1305"),  // info — константа
    )
    io.ReadFull(reader, key)           // 32 байта выхода
    return key, nil
}
```
Порядок аргументов `hkdf.New(hash, secret, salt, info)` — стандартная
сигнатура `golang.org/x/crypto/hkdf`. IKM = сырой пароль строкой (не хеш, не
UTF-8-нормализация, не привязка к устройству). Вызывается: клиент —
`main.go` (`deriveWrapKey(*connPassword)`); шлюз — при каждой
пересборке `wrapKeyStore` из `passwords.json`, раз в 60 секунд
(`main.go-1339`, вызов `deriveWrapKey` внутри `syncFromPasswords`,
`main.go`).

**Отдельно, не путать**: на шлюзе есть ВТОРАЯ, служебная хеш-функция —
`wrapKeyID(password)` = `hex(SHA256("WDTT-WRAP-ID-v1\x00" + password))[:8]`
(`main.go-397`, соль `WDTT-WRAP-ID-v1`, **не** `WDTT-WRAP-v1`) — она
НЕ участвует в протоколе на проводе, это только внутренний идентификатор
записи в локальной таблице ключей (`entries[i].id`, для логов/учёта). Ключ
для расшифровки шлюз всё равно подбирает перебором: `Unwrap()` пробует
`obfsUnwrapPacket` со всеми известными ключами по очереди, пока один не
подойдёт по AEAD-тегу (`main.go-450`) — это отдельный, ДОПОЛНИТЕЛЬНЫЙ
слой обёртки поверх DTLS-байт для релейного пути (см. `main.go-378`:
«клиент оборачивает DTLS-байты в RTP-маскировку перед отправкой через TURN
relay»), устройство которого выходит за рамки этого раунда разведки —
`[вывод, не проверено]` глубже не проверял, отмечаю как существующий
дополнительный механизм.

### 2.4 Набивка

```go
// obfs.go-64 (обе стороны идентично)
pt := uint8(111); pad := 24
if normalizeObfsMode(mode) == "video" { pt = 96; pad = 60 }
```

`PaddingMax`: **24** для audio, **60** для video (`NewObfsConfig`,
`obfs.go-71`). Фактическая длина набивки:
```go
padRand := int(obfsRand.byte()) % cfg.PaddingMax   // obfs.go/:352 → [0, PaddingMax-1]
padTotal := padRand + 1                            // +1 сам байт длины → obfs.go/:355
```
То есть **суммарная набивка (включая байт длины) — `1..PaddingMax`**: `1..24`
для audio, `1..60` для video — подтверждает заявленное в задаче. Источник
случайности — свой пул `obfsRandPool` (крупными кусками, не по одному
`crypto/rand.Read` на пакет — обоснование в `obfs.go-138`), не
`math/rand` (тот дал бы предсказуемый и потому детектируемый паттерн).

**Что ещё меняет `-obfs audio|video`**: по коду — **больше ничего**. Флаг
только у клиента (`main.go`, `obfsMode := flag.String("obfs", "audio",
...)`), значение проходит в `ObfsMode` (`group.go`), используется
единственно в вызове `NewObfsConfig(tp.ObfsMode)` (`session.go,565`,
`session_raw.go`) — который влияет только на `PayloadType` и
`PaddingMax`, как показано выше. SSRC всегда случаен независимо от режима.

### 2.5 DTLS

**Присутствует и активна на обеих сторонах сегодня, а не только «код на
месте»** — это уточнение к постановке задачи, вынесено отдельно в раздел
расхождений.

Где: `github.com/pion/dtls/v3` — шлюз (`main.go-41`), обычный `crypto/tls`-
подобный стек клиента не смотрел отдельно (клиент использует ту же
библиотеку симметрично, обвязка в `session_raw.go` через `dtlsConn` — тип не
выписывал построчно, не требовалось для ответа на вопрос).

**Условия включения** — это НЕ протокольное согласование, а **независимый
локальный выбор транспорта на клиенте** (см. 1.1 и Блок «Обфускация
работает поверх, а не после DTLS решает клиент сам, пробуя кандидатов по
порядку — подробности списка кандидатов относятся к «лестнице», out of scope
этого раунда по прямой договорённости).
- Клиент включает DTLS на РЕЛЕЙНОМ пути по умолчанию **НЕ всегда**: с версии
  3.7 умолчание `defaultRelayNoTLS = true` — релей ПО УМОЛЧАНИЮ идёт БЕЗ DTLS
  (`session_raw_path.go`); явная строка `RELAY_NOTLS="0"` в конфиге держит
  клиента на DTLS (`session_raw_path.go-139,162-167`).
- На ПРЯМОМ пути (без релея) умолчание **обратное** — DTLS остаётся
  включённым: `defaultDirectNoTLS = false` (`session_raw_path.go`).
- Таким образом, заявленное в задаче «снят умолчанием с обоих путей» **не
  совпадает с кодом дословно** — см. раздел расхождений.

**Параметры DTLS-листенера на шлюзе** (`dtls.NewListenerWithOptions`,
`main.go-1469`):
```go
dtls.WithCertificates(cert)                                    // самоподписанный, selfsign.GenerateSelfSigned()
dtls.WithExtendedMasterSecret(dtls.RequireExtendedMasterSecret) // EMS ОБЯЗАТЕЛЕН
dtls.WithCipherSuites(dtls.TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256)  // единственный разрешённый набор
dtls.WithConnectionIDGenerator(dtls.RandomCIDGenerator(8))      // Connection ID, 8 случайных байт
dtls.WithMTU(1100)                                              // MTU DTLS-слоя (НЕ MTU TUN=1200, см. 1.6)
```
Договаривается ли это на проводе или задано константами с двух сторон:
**сертификат, cipher suite и EMS — это параметры DTLS-хендшейка, они
согласуются по протоколу DTLS 1.2 штатно** (сервер предлагает набор,
клиент подтверждает в рамках самого DTLS-рукопожатия — это не наш
собственный протокол, а стандартный DTLS поверх pion). Со стороны клиента
конкретные опции listener'а не смотрел (симметрию не проверял построчно) —
`[вывод, не проверено]` для клиентской стороны конфигурации DTLS.

MTU DTLS = 1100 — это MTU **фрагментации самого DTLS-слоя** (для больших
хендшейк-сообщений), не связан напрямую с MTU TUN=1200 из 1.6: это два
разных слоя одной цепочки инкапсуляции.

## БЛОК 3. Многослот

### 3.1 Открытие слотов — последовательно, без явной паузы

Дополнительные слоты открываются **строго последовательным (не параллельным)
блокирующим циклом**, без `go` и без `time.Sleep` между итерациями
(`session_raw.go-732`):

```go
for i := 0; i < extra; i++ {
    extraLink, slotErr := dialCandidate(link.cand, sessCtx, rawAuthCaps(sessionGen))
    if slotErr != nil {
        log.Printf(...); break
    }
    slots.add(extraLink.conn)
}
```

`dialCandidate` — синхронная функция-замыкание (`session_raw.go`),
каждый вызов ждёт полного дозвона (TURN-аллокация/DTLS-хендшейк +
AUTH-обмен) прежде чем начнётся следующая итерация — то есть «лесенка»
получается ЕСТЕСТВЕННО, за счёт времени самого дозвона
(`handshakeTimeout`/`authTimeout` кандидата, `session_raw_path.go-311`),
**отдельной задержки между слотами в коде нет**. Первая ошибка обрывает цикл
досрочно (`break`) — клиент продолжает с тем числом слотов, что успело
подняться.

Первый слот (основная сессия) вызывает `rawAuthenticate` тем же путём, что
описан в Блоке 1, до входа в этот цикл (`session_raw.go-662`).

`[вывод, не проверено]` Отдельно существует `session_raw_autoslots.go`
(813 строк, не читал построчно) — контроллер, добавляющий слоты ДИНАМИЧЕСКИ
по ходу сессии (упоминается в `session_raw.go` как источник ещё одного
вызова `dialCandidate`). Это, судя по названию и объёму, и есть «лестница»
из следующей задачи — не разбирал глубже по прямой договорённости с
владельцем.

### 3.2 Поколение сессии — 8 случайных байт в hex, один токен на сессию

Подтверждено дословно:

```go
// session_raw_slots.go-135
func newSessionGeneration() string {
    var b [8]byte
    rand.Read(b[:])                       // crypto/rand
    return hex.EncodeToString(b[:])       // 16 hex-символов
}
```

Генерируется **один раз на сессию** — `sessionGen := newSessionGeneration()`
(`session_raw.go`), используется в AUTH КАЖДОГО слота этой сессии,
включая первый (`session_raw.go,725,1255` — все три места передают
одну и ту же переменную `sessionGen`).

**Точное место в AUTH и формат** — четвёртое поле (`caps`), см. 1.2:
```go
// rawAuthCaps, session_raw_slots.go-119
func rawAuthCaps(gen string) string {
    if rawSlots > 1 {
        caps := "echo,multi"
        if gen != "" { caps += ",gen=" + gen }
        return caps
    }
    return "echo"
}
```
То есть полный AUTH при многослоте: `AUTH|<password>|<device_id>|echo,multi,gen=<16hex>`.
При одном слоте (`SLOTS=1`, умолчание) поколение не шлётся вовсе —
`caps == "echo"` (комментарий `session_raw_slots.go-123`: шлюз и так
вытесняет прежнее соединение по IP, как делал всегда).

Разбор на шлюзе — `authGeneration(caps)` (`main.go-1177`): ищет
`gen=` через `strings.CutPrefix` после `strings.Split(caps, ",")`, допускает
алфавит `[0-9a-zA-Z_-]`, длина до `maxGenerationLen=32` (`main.go-79`,
константа) — то есть шлюз готов принять токен ДЛИННЕЕ, чем клиент когда-либо
пришлёт (16 символов); всё, что не проходит валидацию — считается
отсутствующим поколением (`main.go-1176`, возврат `""`).

Fallback при отказе `crypto/rand.Read` — не паника, а
`strconv.FormatInt(time.Now().UnixNano(), 36)` (`session_raw_slots.go-133`)
— заведомо слабее (коллизии при одновременном старте), но явно
задокументированный запасной путь.

### 3.3 Что делает шлюз при новом поколении — подтверждено

Логика в `(g *gateway) register()` (`main.go-820`):
- многослот держится только если И новое соединение, И ВСЕ уже живущие на
  этом IP просили `multi` (`keepOld`, `main.go-754`) — иначе прежнее
  поведение: жёсткое вытеснение одним соединением (`main.go-772`);
- при многослоте: слоты **другого** поколения (`old.gen != c.gen`) **сразу
  выводятся из раздачи** (`retiredAt` ставится немедленно,
  `main.go-812`) — новый пакет туда больше не попадёт (см. 3.5);
  **закрываются же — с задержкой `generationOverlap`**:
  ```go
  var generationOverlap = 3 * time.Second   // main.go
  time.AfterFunc(generationOverlap, func() {
      victim.cancel(); victim.dtls.Close()
  })                                          // main.go-822
  ```
  Подтверждена и константа (3 секунды), и сам механизм отложенного закрытия.
  Причина задержки — гонка между `lookup()` и `Write()` в горутине раздачи
  вниз (комментарий `main.go-92`): без задержки пакет, которому раздача
  уже выбрала это соединение, ушёл бы в закрытый сокет.

### 3.4 Живость — все четыре константы подтверждены по коду

| константа | значение | где | что делает |
|---|---|---|---|
| `lastSeen` | время последнего пакета ОТ клиента (включая keepalive), unix-наносекунды | `main.go`, обновление `main.go,1097` | признак живости слота для раздачи вниз (3.5) и для потолка (3.4б ниже) |

### 3.5 Раздача нисходящего трафика — пачками по 8, с пропуском молчащих

```go
const downlinkChunk = 8    // main.go

func (g *gateway) lookup(dstIP []byte) *client {   // main.go
    ...
    n := cs.rr.Add(1) - 1
    start := (n / downlinkChunk) % uint64(len(conns))     // main.go-917
    fresh := time.Now().UnixNano() - int64(slotStaleAfter)
    for i := 0; i < len(conns); i++ {
        c := conns[(start+uint64(i))%uint64(len(conns))]
        if c.retiredAt.Load() != 0 { continue }            // слот другого поколения — пропуск
        if c.lastSeen.Load() >= fresh { return c }          // первый свежий от точки старта — берём его
    }
    // все молчат — берём самое новое РАБОЧЕЕ (не retired) соединение
    for i := len(conns)-1; i >= 0; i-- {
        if conns[i].retiredAt.Load() == 0 { return conns[i] }
    }
    return conns[len(conns)-1]
}
```

Алгоритм: атомарный счётчик `n` растёт на каждый вызов `lookup`; индекс
стартового слота меняется раз в `downlinkChunk=8` вызовов (round-robin
пачками по 8, как заявлено), но реально отданный слот — **первый живой,
начиная со стартовой позиции по кругу**, а не обязательно сама стартовая
позиция: молчащие (`lastSeen` старше 60 с) и выведенные из раздачи
(`retiredAt != 0`) слоты пропускаются. Если живых нет — стабильно выбирается
самое новое НЕ-retired соединение (детерминированный fallback, не
размазывание по всем).

Восходящее направление (клиент→шлюз) распределяется симметрично тем же
принципом на клиенте, `slotSet.next()`/`nextIdx()`
(`session_raw_slots.go-320`) — та же формула `(n/slotChunk)%len(conns)`,
`slotChunk=8` (`session_raw_slots.go`).

### 3.6 Ротация — `-rotate-after`, умолчание 0 (выключена)

```go

```

- флаг `-rotate-after` (строка: `"8m"`, `"480s"`, `"480"` — секунды числом
  без суффикса тоже разбираются) — `main.go` клиента;
- иначе `ROTATE_AFTER` из `qwdtt.conf` (`session_raw.go-99`,
  `resolveRotateAfter`);
- **`0` (умолчание, если ни флаг ни конфиг не заданы) — упреждающая ротация
  ВЫКЛЮЧЕНА**, сессия живёт, пока жив канал (`main.go-350`, лог явно

- История константы: раньше было жёстко 8 минут (обоснование про TURN
  lifetime 600с оказалось неверным — pion продлевает аллокацию сам каждые
  300с, замер живой сессии — 3ч10м без ротации, `session_raw.go-62`).

**Что происходит в момент ротации** (`session_raw.go-1058`): таймер от
`sessStart` (момент выдачи TURN-аллокации, не момент постройки этой
горутины — хендшейк+AUTH+подъём TUN тоже съедают ресурс аллокации). По
срабатыванию:
```go
plannedRotation.Store(true)   // ДО sessCancel — иначе другие горутины залогируют это как аварию
log.Printf("... ПЛАНОВАЯ РОТАЦИЯ ... Это НЕ сбой: retry-цикл поднимет новую сессию со свежей VK-авторизацией")
sessCancel()
```
Сессия обрывается штатно (`sessCancel()`), retry-цикл в вызывающем коде
поднимает НОВУЮ сессию — с новой VK-авторизацией (новые креды TURN) и, что
следует из 3.2 (`sessionGen` генерируется в `RunRawSession` при каждом
входе, `session_raw.go`), **с новым токеном поколения**. Break-before-
make: старая сессия гасится целиком, только потом поднимается новая
(комментарий `main.go-804` на стороне шлюза подтверждает эту модель со
стороны потребителя — «ротация у него break-before-make»).

### 3.7 Жёсткий верхний предел слотов — есть, отдельный от «восьми»

```go
const maxRawSlots = 9    // session_raw_slots.go-40, клиент
```
Клиентский потолок запроса — **9**, обоснование в коде: «размер группы у
апстрима, выше он и сам не ходит»; свой замер есть только до 4х слотов,
но жёсткого запрета выше нет («потолок здесь про безопасность, а не про
рекомендацию»). `resolveSlots` обрезает любое запрошенное значение до
`maxRawSlots`, если `SLOTS` в конфиге больше (`session_raw_slots.go-86`).

На шлюзе отдельный, БОЛЬШИЙ потолок — `maxSlotsPerIP = 16` (см. 3.4) — это
не предел для одного клиента как таковой, а предохранитель от накопления
«трупов» в списке соединений на IP (в норме недостижим при клиентском
пределе 9, страховка на случай другого способа накопить мёртвые записи,
комментарий `main.go-829`).

Умолчание запроса — **не 8 и не 9**, а `min(4, число ядер)`
(`defaultRawSlots()`, `session_raw_slots.go-61`) — 4 выбрано по замеру

## Расхождения с хендоффами

1. **MTU «асимметрия» (1.6)**. Задача цитирует запись 19.08
   (`ЗАМЕР-ПРОЦЕССОРА.md:296-318`) про асимметрию сторон. Код показывает
   **симметричную константу 1200 на обеих сторонах сегодня**
   (`session_raw.go`, `raw-gateway main.go`). Расхождения на самом
   деле нет — хендофф описывает не текущее состояние констант, а
   ЭКСПЕРИМЕНТАЛЬНО ИЗМЕРЕННОЕ свойство TUN-устройств вообще: MTU интерфейса
   ограничивает только то, что в него пишет ядро СВОЕЙ стороны (и там же
   фрагментирует), а пакет, пришедший от пира и записанный в TUN, /
   принимается независимо от MTU/ (запись хендоффа, подтверждена там же
   отдельным опытом в netns). Это свойство ядра Linux, а не протокола
   Meridian, и не говорит о том, что сегодняшние константы разные — они
   одинаковы. Прав код (константы равны); хендофф прав в своей области
   (поведение TUN) — противоречия по факту нет, только слово «асимметричны»
   в задаче интерпретирует хендофф шире, чем он утверждает.

2. **DTLS «снят умолчанием с обоих путей» (2.5)**. Код показывает, что это
   верно только для РЕЛЕЙНОГО пути (`defaultRelayNoTLS=true`,
   `session_raw_path.go`); для ПРЯМОГО пути умолчание — DTLS ОСТАЁТСЯ
   включённым (`defaultDirectNoTLS=false`, `session_raw_path.go`). Прав
   код: пути асимметричны в противоположном смысле — прямой путь
   консервативнее релейного, а не оба выключены одинаково. Раздел плана
   `/root/ПЛАН-МАРШРУТИЗАЦИИ.md` не смотрел на эту тему отдельно — если это
   расхождение с каким-то конкретным хендоффом, а не с моей же
   реконструкцией постановки задачи, не проверял; отмечаю как факт кода.

3. **Гейтвей слушает DTLS на 56004 «безусловно»** (1.1) — в коде НЕТ
   проверки `if *flagListen != ""` перед запуском `serveDTLS` для порта
   56004 (в отличие от 443 и notls-порта, у которых такая проверка есть,
   `main.go,1354`). Это не расхождение с каким-то конкретным
   хендоффом, а асимметрия в самом коде, которую стоит иметь в виду: 56004
   нельзя выключить флагом, только не передав валидный адрес (что уронит
   `net.ResolveUDPAddr` и он просто не поднимется с логом ошибки,
   `main.go-1456`, а не по дизайну «выключено»).
